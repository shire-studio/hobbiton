# Harvest Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `composer harvest` updates every kit's Composer and npm dependencies (and Hobbiton's own), asks about each new PHP release in Vet once, never applies majors or moves deliberate holds, surveys every kit, and prints one report of majors, holds and problems.

**Architecture:** Pure logic lives in two small ES modules (`scripts/trust.js` for Vet trust files and lock diffs, `scripts/outdated.js` for majors, holds and the report) tested with Node's built in `node:test`. `scripts/harvest.js` orchestrates: guards, phase 1 (update and tend each kit, all prompts here), phase 2 (survey each kit, no prompts), report. Kit preparation is extracted from `survey.js` into `helpers.js` so both share it, and `tend.js` gains a `--check` flag used by the guard.

**Tech Stack:** Node 22+ ES modules, Composer 2.10, Laravel Vet 0.2, pnpm 11, taze 21 (new root dev dependency), `node:test`.

**Spec:** `docs/superpowers/specs/2026-10-23-harvest-design.md`

## Global Constraints

- Release holdback: Vet's `minimum-release-age` is 2 days, so taze always runs with `--maturity-period 2`.
- taze always runs with `--no-github-actions --no-node-version`.
- Deliberate Composer holds are any constraint that does not start with `^` and is not `dev-*` (today: `laravel/framework ~13.34.0`, `nesbot/carbon 3.14.0`, `phpstan/phpdoc-parser 2.3.5`, `spatie/laravel-package-tools 1.93.2`, `fidry/cpu-core-counter 1.3.0`). Never bumped, never edited. `roave/security-advisories dev-latest` is not a hold and is not bumped.
- npm holds are `catalog:` entries in `pnpm-workspace.yaml` (today `vite-plus` and `vite`). Harvest never edits `pnpm-workspace.yaml`.
- A major is a semver major or a minor bump of a `0.x` package. Majors are reported, never applied.
- Edits reach `smials/` only through `tend --once`. A kit that fails in phase 1 is never tended and is raised again so `raised/<kit>` matches `smials/`.
- No new runtime dependencies beyond taze. Tests use `node:test` and `node:assert/strict` only.
- Documentation must not use dashes (— or -) as punctuation.
- Match the style of `scripts/survey.js` and `scripts/helpers.js`: 4 space indent, single quotes, semicolons, a header doc comment with usage, `log()` for output.
- Never commit unless the user has agreed to commits for this work.

## Review Focus

1. **The user ticks nothing in Vet.** Every changed package counts as rejected, is held at its current version, and the kit finishes with no PHP updates. The rejected list shows them all. Test in Task 1 (`rejectedPackages` with an empty trust file).
2. **A rejected package is new in this update** (pulled in by another bump, so absent from the old lock). It cannot be held, so the kit fails with a message naming the package. Test in Task 1 (`holdArguments` returns it in `unheld`).
3. **A package is `require-dev` in one kit and `require` in another.** A seeded grant lands in the section that matches the target kit's lock, never the source kit's. Test in Task 1 (`seedTrust`).
4. **Quoted scoped names in `pnpm-workspace.yaml`** (`'@types/node@26.5.1'`, `'@rollup/rollup-linux-x64-gnu@4.64.8'`) are parsed for both catalog holds and stale excludes. Test in Task 2.
5. **A `0.x` minor is a major on both sides.** Composer reports it as `update-possible`, and taze reports it as `diff: "minor"` with a current major of 0. Neither is applied, and both appear in the majors list. Tests in Task 2.

### Task 1: Vet trust file logic

**Files:**
- Create: `scripts/trust.js`
- Create: `tests/scripts/trust.test.js`
- Modify: `composer.json` (the `test` script array)

**Interfaces:**
- Produces (all pure, all exported from `scripts/trust.js`):
  - `lockVersions(lock: object) -> Map<string, { version: string, dev: boolean }>`: `packages` gives `dev: false`, `packages-dev` gives `dev: true`.
  - `grantsOf(trust: object) -> Map<string, { version: string, hash: string }>` across `require` and `require-dev`.
  - `newGrants(before: object, after: object) -> Array<{ name, version, hash }>`: grants in `after` whose version or hash differs from `before`.
  - `poolKey(name: string, version: string) -> string` returning `` `${name}@${version}` ``. The run's pool is a `Map<poolKey, { name, version, hash }>`.
  - `seedTrust(trust: object, lock: object, pool: Map) -> object`: for each package in `lock` with a pool entry at its exact version, write `{ version, hash }` into `require` or `require-dev` per the lock's section (removing it from the other section). Returns a new object, other top level keys untouched, both sections sorted by key.
  - `pruneTrust(trust: object, lock: object) -> object`: drops grants for packages not in `lock`. Sorted, new object.
  - `rejectedPackages(oldLock: object, newLock: object, trust: object) -> string[]`: names whose version in `newLock` differs from `oldLock` (or is new) and whose grant version is not that new version. Sorted.
  - `holdArguments(rejected: Iterable<string>, oldLock: object) -> { args: string[], unheld: string[] }`: `args` is `['--with', 'name:version', ...]` for each rejected name in `oldLock`, and `unheld` lists the rest.
  - `readJson(file: string) -> object` and `writeTrust(file: string, trust: object) -> void` (`JSON.stringify(trust, null, 4) + '\n'`, matching Vet's own output).

  - `newGrants` returns only the entry whose version changed from `1.0.0` to `1.1.0`, not unchanged ones.
  - `seedTrust` with pool `{ 'acme/tool@2.0.0': hash h }`, a target trust holding `acme/tool` 1.0.0 under `require`, and a target lock that lists `acme/tool` 2.0.0 under `packages-dev` → result has `require-dev['acme/tool'] = { version: '2.0.0', hash: 'h' }` and no `require['acme/tool']`. ### Task 2: Majors, holds and the report

**Files:**
- Create: `scripts/outdated.js`
- Create: `tests/scripts/outdated.test.js`

**Interfaces:**
- `Finding` is `{ name: string, from: string, to: string, kit: string }`. `kit` is a kit name or `'hobbiton'`.
- Produces (pure, exported from `scripts/outdated.js`):
  - `isHold(constraint: string) -> boolean`: true unless it starts with `^` or `dev-`.
  - `bumpablePackages(composerJson: object) -> string[]`: names in `require` and `require-dev`, minus `php`, `ext-*`, holds and `dev-*`. Sorted.
  - `composerFindings(composerJson: object, outdated: object, kit: string) -> { majors: Finding[], holds: Finding[] }` from `composer outdated --direct --format=json` (`installed[]` with `name`, `version`, `latest`, `latest-status`). Holds: constraint is a hold and `latest !== version`. Majors: not a hold and `latest-status === 'update-possible'`.
  - `npmZeroMinors(taze: object) -> string[]`: names of `package.json` resolved entries with `diff === 'minor'` whose current version's major is 0.
  - `npmMajors(taze: object, kit: string) -> Finding[]` from `taze major --json` (`packages[]`, take `type === 'package.json'`, each `resolved[]` has `name`, `currentVersion`, `targetVersion`, `diff`): `diff === 'major'`, or `diff === 'minor'` with current major 0. `from` and `to` drop a leading `^` or `~`.
  - `catalogEntries(workspaceYaml: string) -> Array<{ name, version }>`: entries of the top level `catalog:` block. `npm:<alias>@<version>` reports `<alias>`. Keys may be single quoted.
  - `staleExcludes(workspaceYaml: string, lockText: string) -> string[]`: items of `minimumReleaseAgeExclude:` (quoted or not) whose `name@version` is not followed by `:` or `(` anywhere in the pnpm lock text.
  - `lockMismatches(locks: Record<string, object>) -> Array<{ name, versions: Record<string, string> }>`: packages whose version differs between the given composer locks, or that are missing from some. Sorted by name.
  - `groupFindings(findings: Finding[]) -> Array<{ name, from, to, kits: string[] }>`: grouped by `name`, `from` and `to`, kits in input order, groups sorted by name.
  - `formatFindings(groups) -> string`: one line per group, name, `from → to` and comma separated kits in padded columns, as in the spec:

```
@inertiajs/vue3     2.3.1 → 3.0.0   vue
```

The YAML parsing is line based on purpose: these files are small and machine written, so no YAML dependency is added.

### Task 4: The harvest command

**Files:**
- Create: `scripts/harvest.js`
- Modify: `composer.json` (`harvest` script), `package.json` (`harvest` script, `taze` dev dependency), `pnpm-lock.yaml`

**Interfaces:**
- Consumes: Task 1's `scripts/trust.js`, Task 2's `scripts/outdated.js`, Task 3's `prepareKit` and `tend --check`, and the existing `parseArgs`, `log`, `run`, `rootDir`, `raisedDir`, `smialsDir` and `loadManifest` from `helpers.js`.
- Produces: `node scripts/harvest.js [--vue] [--react] [--svelte] [--livewire] [--api] [--blade]`, exposed as `composer harvest` and `pnpm harvest`. Exits 1 when anything failed.

The run, in order:

1. **Guards.** For each selected kit whose `raised/<kit>` exists, run `tend --<kit> --once --check`. If any exit 1, stop before raising anything and tell the user to tend or raise those kits first. Then, if `git status --porcelain -- smials` or the root has changes, warn that they will mix into the result and carry on.
2. **State.** `pool` (Task 1 pool map), `rejected` (`Set<string>`), and lists for majors, holds, failures, unheld packages and stale excludes.
3. **Hobbiton itself**, only when no kit flags were given: the same Composer and npm steps as a kit, run in `rootDir` and labelled `hobbiton`, with no raise and no tend.
4. **Phase 1, each kit** in `hobbiton.json` order, inside a try/catch so a failure only marks that kit:
   1. `prepareKit(name)`.
   2. **Composer update** (one function, also used for Hobbiton itself), up to 3 attempts:
      - Read the old lock and the trust file.
      - `composer update --no-install --no-scripts --no-progress` plus `holdArguments(rejected, oldLock).args`. This writes the new lock without installing, so Vet does not prompt yet (its release holdback still applies while solving). If `unheld` is not empty, fail the kit naming those packages.
      - Read the new lock, then write `seedTrust(trust, newLock, pool)` to `vet.json`.
      - `composer install --no-progress`, run with `run()`'s inherited stdio so Vet has a TTY and can prompt.
      - On success: `pool` gains `newGrants(trustBefore, trustAfter)`, `vet.json` is rewritten with `pruneTrust(trustAfter, newLock)`, and the step is done.
      - On failure: `rejectedPackages(oldLock, newLock, trust)`. If it is empty, the failure is not a rejection, so fail the kit. Otherwise add the names to `rejected` and retry. After 3 attempts, fail the kit.
   3. `composer bump --no-scripts <bumpablePackages(composerJson)>`, skipped if the list is empty.
   4. For `kit.node`: run `taze major --json` with the global flags and collect `npmZeroMinors`. Then run `taze minor -w` with the global flags plus `-x <names joined by ,>` when there are any. Then run `pnpm update`. Run taze from `node_modules/.bin/taze` under `rootDir`, with `cwd` set to the kit.
   5. `tend --<kit> --once`.
   6. Collect findings: `composer outdated --direct --format=json`, then `composerFindings`. For node kits, `taze major --json` again, then `npmMajors`. For each `catalogEntries` entry, compare it to `pnpm view <name> version` and record a hold when they differ. Then `staleExcludes` against `pnpm-lock.yaml`.
   7. On failure, record it and run `php artisan raise --kit=<name>` so `raised/<kit>` matches `smials/` and the next run's guard passes.
5. **Inertia check.** When vue, react and svelte were all updated, run `lockMismatches` over `smials/inertia-{vue,react,svelte}/composer.lock`.
6. **Phase 2.** For each kit that phase 1 updated, run `node scripts/survey.js --<kit> --tend` and record failures. On a full run, also run `composer test` in `rootDir`.
7. **Report**, in this order, with headings through `log()`: majors (`formatFindings(groupFindings(majors))`), holds (`held at X, Y available`), packages rejected in Vet, packages that could not be held, Inertia mismatches, stale `minimumReleaseAgeExclude` entries, then failed kits. Finish with green `Harvest complete` or red `Failed: ...` and exit 1.

Harvest reads every `vet.json` and `composer.lock` through `readJson` and writes trust files only through `writeTrust`. Vet saves the packages the user ticks even when it fails, which is why a retry does not ask about them again.
